# 迭代记录：真实发生过的缺陷

这份文档记录开发过程中**实际抓到并修复**的缺陷。保留它们有两个用途：
一是回归防线背后都有故事，知道故事才知道防线在守什么；二是它们是
"这个项目真的被一步步跑通过"的证据——从没编译过的代码不会有这些伤疤。

---

## 1. Subprocess 的 waitpid 竞态（最难的一个）

**症状**：引擎正常退出时偶发误报 `引擎未在 1.5s 内退出，强制终止`，
时间戳却显示只过了 10 ms。

**根因**：读线程读到 EOF 后顺手回收了子进程；主线程随后的 `waitpid`
拿到 `ECHILD`（没有这个子进程），被误读成"超时"。两个线程在收尸同一
个进程，谁都没告诉谁。

**修复**：`Subprocess` 内部加 `wait_mu_` + `cached_exit_` + `reaped_`，
收尸只发生一次、结果缓存共享；`RpcClient::reader_loop` 读到 EOF 时**不再
调用 `proc_.wait()`**——收尸是 `stop()` 的职责，读线程只管报告 EOF。

**教训**：竞态 bug 的报错信息往往指向完全无关的方向（这里是"超时"）。
靠日志时间戳对账才定位到。

## 2. Python stdout 块缓冲

**症状**：引擎明明已经算了 8 秒，壳却一个字节都没收到。

**根因**：stdout 连接到管道时，Python 默认 8 KB 块缓冲。响应不够大就
一直攒着。

**修复**：启动参数加 `-u`，环境变量加 `PYTHONUNBUFFERED=1`——**双保险**，
因为只改其一总有办法被绕过（比如用户换了启动方式）。

## 3. `sys.stdin.buffer.read(n)` 的语义陷阱

**症状**：引擎"卡住不动"，不报错也不退出。

**根因**：`read(n)` 会阻塞到**读满** n 字节才返回。而请求帧大多比
读块短，于是永远凑不齐。

**修复**：改用 `os.read(fd, chunk)`——有多少返回多少。这个问题的隐蔽
之处在于它不崩溃、不报错，就是不动。

## 4. 合成源波动率锚定（改了三轮）

见 design-decisions.md 第 7 条。 annual_vol=0.28 实测 53.9% → 37.6% →
30.5%。根因是无条件方差里漏了跳变混合的二阶矩抬升和隔夜跳空的方差贡献，
两处**各自都只差一点，合起来差了近一倍**。靠 stats 输出逐项对账才找到。

## 5. DataHub 递归派发

**风险**：handler 里再 publish 会形成递归派发，环形触发的结果是栈溢出。

**修复**：`thread_local` 深度计数，上限 8 层，超限丢弃并计入统计。

## 6. GUI 层的六处编译错误（一次性暴露）

GUI 代码写完后一直没有进入构建（`FINPULSE_BUILD_GUI=OFF` 的状态持续了
整个开发期）。第一次用 Qt6 真实编译，6 个 TU 里的错误一次全冒出来：

| 错误 | 根因 | 修复 |
|---|---|---|
| `Version.h: No such file` | include 路径少了 `core/` 前缀 | 改成 `core/Version.h` |
| `std::string` → `QVariant` | Qt 不做隐式转换 | `QString::fromStdString` |
| `QString::arg(std::string)` | 同上 | 同上 |
| `std::max(long long&, const int64_t&)` | 模板推导冲突（`int64_t` 在 Linux 是 `long`） | 显式 `static_cast<long long>` |
| `incomplete type 'QDateTime'` | 只用了前向声明 | 补 `#include <QDateTime>` |
| `Subscription` 三参构造不存在 | 构造签名是 `(hub, id)` 两参，多传了个 `0` | 去掉多余实参 |

**教训**：**"代码写完了"和"代码能编译"是两件事**。GUI 层的存在感很低
（一直没参与构建），错误就藏在里面。可信度来自能跑起来的二进制，不是
看起来完整的源码。

## 7. GUI 的 nullptr connect（运行期才暴露）

**症状**：启动时打印
`QObject::connect(...): invalid nullptr parameter`，十字光标联动失效。

**根因**：`connect(chart_, ...)` 写在 `buildToolBar()` 里，而
`buildToolBar()` 在 `buildUi()` 中**先于** `chart_` 创建被调用——
那时 `chart_` 还是 nullptr。Qt 对此只打一行警告，不崩溃，功能静默失效。

**修复**：把 connect 移到 `chart_` 创建之后，并加注释说明顺序约束。

**教训**：静默失效比崩溃更危险——崩溃有人修，静默失效用户只会觉得
"这功能大概本来就这样"。

## 10. 「回放行情」是个摆设（首次真人检查时发现）

**背景**：项目交付后让真人上手点了一遍。日志里出现了这组数字：

```
15:14:51.068 [replay] 装载 500 根 SYNTH 的历史数据 …
15:14:51.069 [replay] 回放结束，共发布 500 根     ← 1 毫秒放完 500 根
```

**根因（两层，叠在一起才构成"功能失效"）**：

1. `MainWindow::startReplay()` 用的是 `ReplaySource` 的默认
   `Options{}`，而 `speed = 0.0` 的语义是"全速、不 sleep"。
   500 根在 1ms 内全部砸进 DataHub——表格清空又瞬间填满，
   图表一动没动。功能从实现者视角是"能跑"，从使用者视角是"坏了"。
2. 更深一层：GUI **根本没有订阅 `market.kline.**`**，只订了
   `market.quote.**`。也就是说，就算把速度调慢，蜡烛图也不会
   动——只有右侧表格在跳。回放功能在图表上从未生效过。

**修复**：

| 改动 | 说明 |
|---|---|
| 工具栏加「回放速度」下拉（全速/20ms/60ms/200ms） | `userData` 直接存间隔毫秒数，`currentData().toInt()` 一行取出 |
| `CandleChartWidget::beginStreaming()` / `appendBar()` | 图表从空开始逐根生长；铺满 120 根后变成滚动窗口。刻意不改 `offset_`——用户手动缩放过就不拽回去 |
| `MainWindow` 订阅 `market.kline.**` | K 线与行情本来就是两个主题，订阅者各取所需——这个拆分终于用上了 |
| 回放结束恢复分析视图 | `applyChartView()` 从 `applyAnalysis()` 里拆出来，靠缓存的 `last_bundle_` 原样贴回，省一次引擎往返 |
| 收尾统一到 `market.replay.done.*` 订阅回调 | 原来线程 lambda 和订阅回调**两处各改一半**界面状态，必然漏 |
| `runAnalysisAsync()` 先停回放 | 回放往"分析结果的 500 根"后面追加，和重新分析同写一张图必然互相踩 |
| 状态栏显示 `[回放中] K 线 N / 行情 N` | 两个独立订阅两个独立计数，数字对不上就说明有路径掉帧 |

**验证**：`--screenshot` 加了 `--replay <ms>` 参数——定时器到点后
**找到按钮并 `click()`**，走的是和用户点击完全相同的路径，
不给生产代码开测试后门。两张截图分别抓到回放进行中（68 根 / 3.98s，
节拍 ≈ 58ms 符合 60ms 设定）和放完后的恢复画面。

**教训**：
- "能跑"和"能用"之间隔着一次真人上手。自动化测试全绿的项目，
  照样能把一个按钮做成摆设——因为没有任何测试断言
  **用户点了之后界面看起来会动**。
- 视觉证据要抓"过程"而不是只抓"结果"。`--screenshot` 之前只截
  静态分析图，回放链路从未被验证过。

## 11. 事件说明文字整段消失（接 CLI 时发现）

**症状**：CLI 的智能体研判一节里，事件流只剩光秃秃的事件名
（`agent.round.done`），后面该跟着的"第 1 轮结束（无人改口）"一个字都没有。
没有报错、退出码 0、事件也确实收到了——看起来"事件通道通了，只是没写说明"。

**根因**：描述表的键写的是**语义名**（`role.start`），而 Python 侧推到线上
的事件名带传输层前缀（`agent.role.start`，用它和未来的其它事件域区分）。
于是**每一条**分支都不命中，`describe()` 返回空串，调用方按约定只打事件名。
整段说明文字就这么静默消失了。

这类缺陷靠"跑一遍看输出"抓不到：输出看起来"就是没写说明"，而不是"写了但错了"。
唯一可靠的抓法是把"引擎推的**每一种**事件名都必须能匹配到一条说明"写成断言。

**修复**：

| 改动 | 说明 |
|---|---|
| 前缀在传输层边界剥掉 | `event_text::strip_prefix()`，只剥一层 |
| 文案抽成 `src/app/EventText.h` | 纯函数、无 IO，CLI 与 GUI **共用一份**，两处说法不会漂移 |
| 元性质测试 | 把引擎推的 11 种事件名列成清单，逐个断言"必须产出非空说明"；Python 侧新增事件忘了加文案就会红在这条 |

**教训**：事件名的前缀是传输层约定，就该在传输层边界处理掉，别让展示层
自己去对"带不带前缀"这种事。以及：一个"每个事件都该有文案"的元性质断言，
比十几条逐字段的格式断言更能防住这类静默失效。

## 12. AgentService 析构后的事件处理器是 use-after-free

**症状**：无。这是接 GUI 时**顺着析构顺序审出来的**，从未真正崩过——
而这正是它危险的地方：一旦有事件在服务析构之后到达，就是一次野指针写，
表现完全不可预测。

**根因**：`AgentService` 构造时往 `PyEngine` 上装了一个事件处理器，
lambda 直接捕获 `this`。析构函数的注释写的是：

> 析构时不主动拆掉事件处理器……留一个已失效的 handler 是安全的
> （它只是往总线发消息）

**这个理由是错的。** 处理器要读 `seq_`、要写 `forwarded_`、要拿 `hub_`，
桩桩件件都经过 `this`。"它只是往总线发消息"——发消息用的总线指针就存在
`this` 里。引擎的生命周期由调用方掌握，完全可能比 `AgentService` 活得久。

**修复**：把处理器真正要碰的那点状态（序号、转发计数、最近主题、总线指针）
单独拎成一个 `Sink` 结构，用 `shared_ptr` 持有；处理器**只捕获 `weak_ptr`**。
服务析构 → weak 失效 → 残留的处理器退化成空操作。既不用拆处理器
（那要处理"读线程正在回调中"的竞态），也不再碰任何已释放的内存。

**验证**：测试里先建服务、立刻销毁，然后**绕过 C++ 门面直接用 RPC** 触发一次
智能体运行——于是 Python 往这条已经"没有主人"的处理器上推事件。断言：
进程不崩，且那批事件一条都没到总线上（计数不变）。旧的实现跑这个用例
就是一次野指针写。

**教训**：注释里"这样做是安全的"这种话要经得起追问——**安全在哪一层**？
"只是发消息"不是理由，除非发消息不经过 `this`。凡是生命周期由别人掌握的
回调，一律按"我死了它还活着"来设计。

## 13. 紧凑日期格式让 Tushare 整批静默回落缓存

**症状**：`--source tushare` 每次都打印"本地缓存 —— 不是实时数据"，
即使 token 配好了也一样。没有报错——因为数据源设计上允许回落，
回落原因只写在 provenance 里，一查 detail 才发现是"解析 0 行"。

**根因**：Tushare `daily` 接口返回的日期是紧凑格式 `20240102`。而
`parse_datetime_ms` 只认 `YYYY-MM-DD` 和 `YYYY-MM-DD HH:MM:SS` 两种写法——
"紧凑格式"此前是在 `csvfile` 数据源里**预处理**的（通达信导出的兼容逻辑），
不是时间解析的通用能力。于是 Tushare 拿到的每一行日期都解析失败，
坏行被逐条跳过，最终 0 行 → 触发回落。三层静默叠加（坏行跳过 → 空结果
→ 回落缓存），每一层单看都"合理"。

**修复**：把紧凑格式**下沉**到 `timeutil.parse_datetime_ms`（时间解析只有一处），
`csvfile` 删掉自己的重复实现。补了 `test_timeutil` 的格式矩阵用例
（三种写法、跨年一致、非法输入），以及 Tushare 侧的解析用例。

**教训**：**同一件事只能有一个实现处**。"CSV 兼容"和"日期解析"的边界
划错了，功能就只在第一个用户（CSV）那里被测过。另一个教训：允许回落
的数据源必须把回落原因打印到用户眼前——否则"实时数据源永远出缓存"
这种问题会被当成"大概本来就这样"。

## 14. 拖动切换的 release 顺序：先清状态再算位移，释放点位移被漏算

**症状**：单元测试 `释放点离得远也算拖动` 失败——从按下到释放位移超过
点击阈值的操作，被判定成了"点击"，拖动模式被误切换。

**根因**：`DragToggle::release(x)` 原实现是**先** `active_ = false` **再**
`move(x)`。而 `move()` 开头有 `if (!active_) return;` 的短路——
状态先清了，释放点这次的位移就永远进不了判定。顺序反了，
"按下点 → 释放点"的距离判定退化成了"按下点 → 最后一次移动"的距离。

**修复**：调换顺序——先 `move(x)` 记录释放点位移，再清 `active_`。
并把这段因果写进注释：**release 里的顺序不是风格问题，是语义问题**。

**教训**：状态机的每一步转移都有先后依赖，"清理"放在最后做通常是对的。
这条防线是那 9 个 `ChartInteraction` 用例里最不起眼的一个撑起来的——
单看"释放"这个函数，两种顺序都能编译、多数操作手感一致，
只有边界用例能把它揪出来。

## 15. 对话式研判接线时暴露的三个问题

**背景**：把 AI 研判页从"一排控件 + 一个只读文本框"改成"对话气泡 + 独立设置对话框"。
改动本身不大，但两处真实缺陷在编译期和首轮测试里各被抓到一个，第三个藏在渲染层。

### 15.1 `Message.assistant()` 根本不存在（首轮 Python 测试抓到）

**症状**：`agent.chat` 一带多轮历史就抛
`AttributeError: type object 'Message' has no attribute 'assistant'`。
而且只在历史里出现 assistant 消息时才炸 —— 单条 user 提问的用例全绿。

**根因**：`Message` 只有 `system()` / `user()` / `tool_result()` 三个静态构造器，
`agent.chat` 里回放历史时想当然写了 `Message.assistant(text)`。
`agent.chat` 是新加的 RPC，此前**没有任何代码**需要构造 assistant 消息 ——
角色运行时里的模型回复是直接从 `LlmResponse.text` 取的，从不过 `Message`。

**修复**：补上 `Message.assistant(text, *, tool_calls=None)`，并顺手让
`user()` / `assistant()` / `system()` 三个构造器凑齐。测试里也补了一条
"系统提示词只出现一次且在历史之前"的多轮用例 —— 它正是当初漏测的形态。

**教训**：新 RPC 的测试必须覆盖**多轮**形态。单轮用例绕过了整条历史回放路径，
而那条路径恰恰是唯一会用到缺失构造器的地方。

### 15.2 `class QFormLayout*` 写在命名空间里声明出了另一个类型（编译期抓到）

**症状**：`SettingsDialog.cpp` 里十几处
`error: invalid use of incomplete type 'class fp::gui::QFormLayout'`。

**根因**：头文件里把私有方法写成了

```cpp
void buildBackendGroup(class QFormLayout* form);
```

`class X*` 是**详细类型说明符**：在命名空间 `fp::gui` 里这样写，会在
**这个命名空间里**声明一个名叫 `QFormLayout` 的新类 —— 它和全局的
`::QFormLayout` 永远不是同一个类型。于是 `.cpp` 里 `#include <QFormLayout>`
引入的是全局那个，参数表里的却是 `fp::gui::QFormLayout`，一调 `addRow` 就是
"incomplete type"。

**修复**：在全局作用域正常前置声明 `class QFormLayout;`，参数表写
`QFormLayout*`。错误原因写进了头文件注释，防止下一个人照着旧样子再写一遍。

**教训**：`class X*` 这种"省一行前置声明"的写法**只能在全局作用域用**。
它落在哪个命名空间里，就会在那个命名空间里凭空造出一个新类型，
而报错指向的是使用处，不是声明处 —— 顺着报错行号查是查不到根因的。

### 15.3 欢迎语里的行内代码被原样显示（出图后肉眼发现）

**症状**：首条欢迎气泡里 `` `/debate` `` 的反引号原样出现在屏幕上。

**根因**：`ChatRender::render_text()` 刻意只支持三种 Markdown 写法
（`**粗体**`、行首 `#`、行首 `-`/`*`），不含行内代码 —— 这是设计决定
（"半吊子解析器把 `2*3*4` 吃掉比不解析更糟"），不是缺陷。
问题在于**写欢迎语的人**（也是我）按完整 Markdown 的习惯用了反引号。

**修复**：改文案，不用反引号。没有给渲染层加行内代码支持：
这条能力只有这一个消费者，为它扩解析器的收益是负的。

**教训**：**渲染层支持什么，写文案的人就只能用什么**。两者没有契约检验，
只能靠把渲染结果真的画出来看一眼 —— 这正是 `--ask` 截图钩子存在的理由。

## 16. 报告里的「年化波动率 0.15%」——两种比率表示约定相撞

**背景**：有人问「投委会到底是不是多 agent，怎么跑起来不好用」。查这个问题的
时候顺手把规则后端的输出逐段读了一遍，在第 5 段看到：

```
当前年化波动率 0.15%，处于自身历史的 22.09% 分位，判定为 偏低（区间 0.05% ~ 0.41%）。
```

### 16.1 症状有两个，根因只有一个

**症状 A（数字错）**：贵州茅台的年化波动率不可能低于 1%。同一份报告的第 4 段
（风险概览，取自 `stats`）写着 22.46% —— 同一个量，两段差了 100 倍。

**症状 B（护栏误报）**：同一次运行的护栏报了一条
`[warning] flow_analyst.number_provenance：1 个数字无法溯源`，detail 指名
`22.09%`。而 22.09 就是 `0.2209 × 100`，那个数字**明明来自工具输出**。

两个症状都出在 `rule_based._fill_vol_regime` 这一处。引擎里**比率有两种表示
约定**，且都没有写进字段名：

| 来源 | 约定 | 例 |
|---|---|---|
| `stats` / C++ 的 `change_pct` | 字段名带 `_pct`，**已经是百分数** | `ann_vol_pct = 22.46` |
| `flow.volatility_regime` | **小数** | `current = 0.1531`（= 15.31%） |

`_pct()` 这个格式化函数的语义是「给已经是百分数的值补一个 `%`」——套在第一种
上是对的，套在第二种上就把 15.31% 写成了 0.15%。而 `percentile` 那一格因为
作者**手写了一个 `* 100`**，数字是对的，但写进文本的 22.09 与工具输出里的
0.2209 在溯源时对不上，于是护栏如实报告「找不到出处」。

### 16.2 为什么难发现

三个条件同时成立，掩盖了它：

1. **不崩溃**。渲染层对 `None` 有兜底，对量级没有概念；
2. **读起来通顺**。整段话语法完整、语气专业，只有数字是错的；
3. **护栏的误报看起来像另一个问题**。看到「22.09% 无法溯源」，第一反应是
   「模型编了数字」，而这次的规则后端根本不编数字。于是去查模型，查错了方向。

第 3 点最值得记：**一条错误的告警会把注意力引向错误的地方**，比没有告警更费时间。

### 16.3 修复

**渲染层**：新增 `_frac_pct()` 专门渲染小数形态的比率，与 `_pct()` 分开。
刻意**不做**「自动判断量级」的合并版：`0.5` 到底表示 50% 还是「0.5 倍」，
只有字段本身知道；让格式化函数去猜，猜错的时候没人看得出来。单位由**调用点**
显式声明，责任落回写代码的人身上。

**护栏层**：`NumberProvenance._matches` 增加一条——当字面量**带 `%`** 时，
额外用 `值 ÷ 100` 去池子里比一次。同一个比率的两种写法不是两个数。

这一处本来想省掉（改渲染就够了），但算了一下：不改的话，**每次**跑量价类
角色都会误报一条。一条每次都出现的告警，用户几天内就会学会无视它 ——
那等于把整条溯源检查废掉，比不检查更糟。所以这层换算是必要的，不是宽容。

只对带 `%` 的字面量换算，写成 `5046` 时不会去匹配池子里的 `50.46`，
没有顺手把普通数字的容差一起放宽。

### 16.4 顺带补上的测试缺口

查这个问题时发现：**投委会走真实 LLM 后端那条路径没有任何测试**。
`rule_based` 是模板引擎，不需要解析模型回复；一旦接上真模型，多出来
「HTTP 请求 → 模型返回 tool_calls → 引擎执行工具 → 结果回填 → 再请求 →
解析段落/方向」一整条链，而这是用户真正在用的那条。

新增 `python/tests/test_agent_llm_path.py`（6 例，本进程起假端点，不联网）：
七个角色运行全部走外部模型、工具循环真的发生、交叉质证把委员结论交付回去、
**主席拿得到全部委员的结论**、第 1 轮看不到别人的结论（避免锚定）、token 记账。

其中「交叉质证」那条是重点：只看最后的结论表，**分不出**它是多 agent 还是
「并行作答再计票」——两种做法都能给出三行方向。所以测试直接检查**发出去的
提示词**：第 2 轮的请求里必须带着 `### <其他委员>` 的注入块，而第 1 轮必须没有。

### 16.5 教训

- **格式化函数不该猜单位**。同一个量在链路上有两种写法时，必须有一处是唯一的
  约定；靠「函数聪明一点」来兜住两种，就是把错误藏进一个没人会看的地方。
- **同一个数字在同一份报告里出现两次，是免费的校验**。风险段写 22.46%、
  波动率段写 0.15%，这两句话放在一起就是 bug 报告。值得给报告加一条**自洽性
  检查**：同一指标的多处引用必须一致（已记入待办，本次未做）。
- **护栏误报要当 bug 修**，不能当噪声忍。它的成本不是一条日志，是训练用户
  忽略所有告警。

## 17. 接上 DeepSeek 后投委会全军覆没：`terminal.live_quote` 里的点号

### 17.1 现象

用户配好 DeepSeek 密钥，跑一场标准投委会，三个委员全部"弃权"，
报告顶上一行：

```
[error] 有效委员 0 位（[]），未达 quorum 2 位。
未形成有效判断的委员：technical_analyst：未产出结论（后端调用失败：
HTTP 400 调用 https://api.deepseek.com/v1/chat/completions 失败:
{"error":{"message":"Invalid 'tools[2].function.name': string does not match
pattern. Expected a string that matches the pattern '^[a-zA-Z0-9_-]+$'."}}）
```

三个角色的报错里，下标分别是 `tools[2]`、`tools[3]`、`tools[2]`。

**注意这里有两件事同时成立，别把它们混在一起：**

1. 编排层的行为是**对的**。委员集体拿不到结论时它拒绝出一个方向，
   而不是把"密钥/网络/后端故障"包装成一条投资意见。这条规则前一版
   刚写下来，这次正好被真实故障验证了一次。
2. 但故障本身是**我们的**：工具名里的点号过不了服务端的字符集校验。

### 17.2 根因

`terminal.live_quote` —— 远程工具的名字带点号。`function.name` 的协议
约束是 `^[a-zA-Z0-9_-]+$`，点号不在里面。技术面分析师的工具清单是
`[indicators, stats, terminal.live_quote]`，所以它报 `tools[2]`；
量价分析师是 `[..., flow, terminal.bus_stats]`，报 `tools[3]` ——
下标与清单一一对上，根因没有歧义。

点号是我们自己挑的，而且是**刻意的**：配置里一眼能分辨"这个工具跑在
C++ 终端里"，`ToolBridge` 的令牌作用域也按这个名字授权，测试里还专门
钉了"远程工具一律带 `terminal.` 前缀"这条约定。

所以修法不是改名，是**在边界上翻译**：
`terminal.live_quote` → `terminal_live_quote`（线上），回程再翻回来。

**为什么会有"回程"**：模型看到的是线上名，它回的 `tool_call` 也是线上名。
注册表、`tool_results`、护栏、轨迹、记忆全按原名工作 —— 只改一边，
症状会变成"工具调了但结果查不到"，比现在更难查。

### 17.3 翻译放在哪一层（改错过一次）

第一版把翻译放在**角色运行时**（`roles.py`）：构建目录时换名，
派发工具时翻回来。测试全绿，但有两条测试红了：

```
test_terminal_evidence_renders_bridge_data
  '600519' not found in '本角色未声明任何终端侧工具（terminal.*）……'
```

原因是 `rule_based` 后端也吃这份目录 —— 而它是按**名字**查固定参数、
按**名字**取工具结果的。名字被在角色层改掉之后，它 `data.get("terminal.bus_stats")`
永远取不到值，于是规则后端的"终端证据"段退化成"本角色未声明任何终端侧工具"。

**这是一个提示，不是意外**：点号对我们自己毫无问题，只对"要 POST 出去"
这一个场景非法。所以翻译属于**传输层**。改到 `openai_compat` 里之后，
规则后端、引擎内部、轨迹、界面全部按原名工作，只有真正发出去的那份 JSON
被改写。一个 provider 改动覆盖所有 OpenAI 兼容服务商（deepseek / moonshot /
dashscope / openrouter / groq / ollama / 自建网关）。

传输层要改的**不止工具目录**，而是三处（同一个字段的三个方向）：

| 位置 | 为什么 |
|---|---|
| `tools[].function.name` | 第一次请求就发出去，DeepSeek 就是拒在这里 |
| assistant 消息的 `tool_calls[].function.name` | 第二轮会把第一轮的历史回填 |
| `role='tool'` 消息的 `name` | 工具结果的署名 |

只改第一处的话，第一轮能过、第二轮 400 —— 而且报错位置从 `tools[2]`
变成 `messages[3]`，看起来像另一个问题。

### 17.4 两个自检

线上名由 `to_wire_name()` 机械生成（非法字符 → 下划线）。它**不保证可逆**
（`a.b` 与 `a_b` 撞同一个名字），所以回程用一张对照表而不是反推。表建起来时
顺手挡两件事，都是配置错误、都当场抛：

- 两个工具名撞同一个线上名 → 发出去之后模型只回一个名字，无法区分该调哪个；
- 线上名超过 64 字符 → 协议上限。

为什么不让它"发出去再看服务端怎么说"：等它变成某次研判的 HTTP 400，
现场只剩一句"服务端拒绝了这个请求"，与真正的原因隔着好几层 —— 这次就是。
`default_registry()` 里也加了一句自检，装机就验证一遍。

### 17.5 测试：让假端点比真服务商还严格

原来的假 LLM 端点对工具名**来者不拒**。这正是这类 bug 能活到今天的原因：

```
真实世界：名字带点号 → 服务商 400 → 报告里全是"后端调用失败"
假服务器（宽松）：名字带点号 → 一路绿灯 → 测试全绿
```

所以把假端点改成**照抄 DeepSeek 的规则**：`function.name` 不匹配
`^[a-zA-Z0-9_-]+$` 就回 400，错误体同形。离线环境因此能复现线上故障。

新增/改动：

- `test_agent_llm_path.py::TestRemoteToolWireNames`（4 例）：让假模型去点
  **带点号的那个**远程工具（它永远排在角色工具清单末尾）。断言发出去的
  是下划线形态、派发回来的是注册表原名、以及报告里不再出现"后端调用失败"。
- `TestWireEncoding`（5 例）：三处换名逐个断言，外加"回程翻译"与
  "模型编的工具名原样带回"。还有一条钉住"换名不能污染内部对象"——
  `_wire_message` 是复制出去改的，原 `Message` 必须保持原名；另一条钉住
  tool 消息**只带协议定义过的三个字段**（见 17.7）。
- `test_agent.py::TestToolWireNames`（9 例）：注册表层的约定 —— 每个工具的
  线上名都合法、`catalog()`（原名，界面用）与 `wire_catalog()`（线上名，
  发出去用）**必须不同**、撞名/超长报错、**拿真实角色配置跑一遍**。
- `tools/mock_llm.py` 同步加校验，并支持 `FINPULSE_MOCK_TOOL=last`
  手动压测远程工具那条路。

**回归测试有效性验证过**：把 `to_wire_name` 换成恒等函数（= 回到修复前），
`TestRemoteToolWireNames` 4 例全红，报错与原故障逐字一致：

```
('tools[2].function.name', 'terminal.live_quote'),
('tools[3].function.name', 'terminal.bus_stats'),
('tools[2].function.name', 'terminal.data_quality')
```

下标与真实报错完全对上。也就是说这不是"补了一个看着相关的测试"。

### 17.6 顺带修掉的测试替身缺陷

假 LLM 端点原来是**单线程** `HTTPServer`，而投委会的三个委员是并发跑的。
在本地端口上表现为 `ConnectionResetError`，排查方向很容易跑偏（"是不是
引擎的并发有问题"）。改成 `ThreadingHTTPServer`：真服务商当然并发处理，
替身不该成为瓶颈。

### 17.7 顺手去掉一个"我们自造"的字段

查 DeepSeek 的工具调用文档时发现：它的官方示例把工具结果 append 成这样 ——

```python
messages.append({"role": "tool", "tool_call_id": tool.id, "content": "24℃"})
```

三个字段。而我们发的是四个：`Message.name` 也被写进去了（
`Message.tool_result(call_id, name, payload)` 会把工具名带上，用于内部追溯）。

OpenAI SDK 的 `ChatCompletionToolMessageParam` 同样是这三个键 ——
也就是说 `name` **不在协议定义里**。这是个隐患里更隐蔽的一种：它属于
"多送一个字段，赌服务端宽容度"，赢了没有任何收益，输了整次研判作废。
`tool_call_id` 已经足够把结果和调用对上，`name` 纯属冗余。

所以线上形态里去掉它（`Message` 内部保留，轨迹与测试照旧用）。
假端点同步加了这条严格校验：tool 消息出现未定义字段就 400。

### 17.8 教训

- **配置错误要在装机时报，不要留到运行时**。撞名、超长都是静态的，
  却要等到某一场研判的 400 才暴露——那时现场信息已经被削薄到只剩一句
  服务端拒绝。
- **假替身必须比真服务商严格，不能更宽松**。宽松的替身会主动掩盖一整类
  集成故障，而且掩盖得非常干净：测试全绿。
- **翻译放在"只有那里才成立"的那一层**。点号只对 HTTP 请求非法，就翻译在
  HTTP 那一层。放到更上层会连带改坏所有"不需要翻译"的调用方——这次是
  规则后端，它的表现还不是报错，是一段看起来正常的"本段没有内容"。
- **只改一个方向 = 半修复**。同一个字段（工具名）在协议里出现三次，
  改一次能过第一轮、第二轮照样炸，且报错位置变了，像是另一个 bug。

## 18. 工具名修好之后，投委会第二次全军覆没：第 2 轮被 max_tokens 截断

### 18.1 现象

上一节刚把工具名的点号问题修掉。用户配好 DeepSeek 重跑，报告顶上是：

```
会议问题  [error] 有效委员 0 位（[]），未达 quorum 2 位。
         未形成有效判断的委员：
         technical_analyst：未产出结论（（第 2 轮输出被 max_tokens=1600 截断））；
         flow_analyst：未产出结论（（第 2 轮输出被 max_tokens=1400 截断））；
         risk_officer：未产出结论（（第 2 轮输出被 max_tokens=1600 截断））。
推理后端  deepseek ×6    token 23633 → 10146
```

第 1 轮技术面已经给出 `BEARISH`，第 2 轮三个委员全被截断 —— 决议作废，
33k token 打水漂。

**注意这次服务商没有任何过错**：请求全部被接受、模型也真的回答了。
故障完全在我们这一侧，而且是两个叠在一起。

### 18.2 根因一：轮数预算比工具预算还小

`roles.py` 里写死：

```python
MAX_TURNS = 4        # 注释写的是"2 轮是常态，给到 4 是容忍多补一个工具"
```

而角色的 `max_tool_calls` 是 6。**4 < 6** —— 这个配置自相矛盾：一边允许它
调 6 次工具，一边只给它 4 轮说话的机会。

为什么上一版看起来没问题？因为它是照**规则后端**推的：规则后端一轮就把
角色声明的工具全部调完（3-4 个一次点完），于是第二轮必然有余量写报告。

真实 LLM 不这么做。它最常见的做法是**一轮只调一个工具**。量价分析师声明了
4 个工具，于是：

```
轮 1 → flow          轮 2 → indicators
轮 3 → stats         轮 4 → terminal.bus_stats
（轮数用光，报告没写）
```

收尾一句"（达到最大轮数 4，可能存在工具循环）"。模型自己每一步都是对的，
错的是预算。

**修法**：轮数从工具预算推导，不写死。

```python
def turn_budget(max_tool_calls: int) -> int:
    return min(TURN_HARD_CAP, max(2, int(max_tool_calls)) + 2)
```

同时补一条：**工具预算用完之后要把工具真的撤下来**，并明确告诉模型"现在
写报告"。预算用完还继续递工具，模型只会继续要——而每一轮都是真实计费调用。

### 18.3 根因二：截断被当成"整份报告不可用"

原来的代码：

```python
if response.finish_reason == "length":
    run.error = (run.error or "") + f"（第 {turn} 轮输出被 max_tokens=… 截断）"
```

而 `RoleRun.ok = error is None and text`，`is_effective` 又要求 `ok`。
于是**"没写完" 和 "没写" 被一视同仁**：一份五段齐全、只在末尾被切掉的
报告，和一个字都没写的报告，得到同一个下场。

判据错了，而且错得不易察觉——因为它看起来像"严格"。

**修法**：截断只记 `run.truncated`，配一条 **warning** 级护栏
（`output_truncated`）。"这份报告能不能用"交给**缺段护栏**回答，那才是它的
职责。于是：

| 情况 | 判罚 | 依据 |
|---|---|---|
| 写满五段、末句被切 | 警告，照常计票 | `output_truncated` (warning) |
| 真的缺段 | error，不进计票 | `section_completeness` (error) |

顺带把各角色的 `max_tokens` 从 1400/1600/1800 提到 2600/3000/3200。截断是
"预算不够"的症状，只改判定不改预算等于把报警器拆了。

### 18.4 第三条：后一轮的失败不该追溯地否定前一轮

这才是让**整场会议归零**的直接原因。`debate()` 的 quorum 建在
**最终一轮**的 `effective_runs` 上，而第 2 轮三个人全被截断，于是第一轮
成立的结论**一起作废**。

两轮之间并没有出现任何新事实。第 2 轮的失败凭什么否定第 1 轮？

**修法**：交叉质证轮结束时，对本轮没能产出**可用**结论的委员，如果它上一轮
的结论仍然有效，就沿用上一轮。判据用 `is_effective` 而不是"有没有正文"——
一份被截断、少了段落的报告确实有正文，但它连计票都不该进。

沿用**必须可见**，否则会议记录会撒谎：

```
会议问题  [warning] 第 2 轮以下委员未产出可用结论，已沿用其第 1 轮立场：
          flow_analyst（本轮未产出可用结论（输出被 max_tokens 截断，段落没写完，
          缺：「波动率状态、背离、终端证据、置信度」））；…
```

另外附送一条省钱规则：**没有对等结论可质证的委员，第二轮不重跑**。它拿到的
提示词与上一轮一字不差（对等结论块是空的），工具输出也是同一份，再问一遍
只会烧掉一整轮。上一轮全员失败时，这条规则会把整个第二轮省掉。

### 18.5 关于"烧了很多 token"

除了上面两处**纯浪费**（截断后整场作废、无质证对象时的空跑），又加了两条
输出侧的收紧——输出 token 是账单上最贵的一半：

- 任务提示词里写明**输出预算**（`段落数 × 200 字`，并说明"超出会被截断，
  反而丢掉最后一段"）。输出越界是最贵的失败：要么丢段，要么逼我们重跑一遍。
- **交叉质证注入的对等结论截到 900 字**（主席那份仍是 1600 字）。委员要做的是
  "回应结论"，给它全文只会换来一段同样长的回话——那正是输出撑爆 `max_tokens`
  的由来。这一块也是提示词里最大的一项，且每轮、每次调用都要重发。

### 18.6 报错信息也要能干活

顺手改了 quorum 不足时的原因措辞。原来只有一句：

```
risk_officer：护栏报了 error 级问题，报告不可用
```

"报告不可用"这四个字对排查毫无帮助。现在会把真原因写出来，且**只在一处
实现**（`orchestrator.why_unusable`），免得"会议问题"和"沿用理由"两处说法漂移：

```
risk_officer：护栏报了 error 级问题，报告不可用
              （输出被 max_tokens 截断，段落没写完；缺：尾部损失、模型可信度…）
```

### 18.7 测试

新增 11 例（Python 511 → 522）：

- `test_agent.TestOutputBudget`（7 例）：轮数预算 ≥ 工具数；"一轮只调一个工具"
  也写得完报告；预算用完后工具被撤下并催收尾；截断但段落齐全仍可用；
  截断到缺段才算不可用；提示词里写了输出预算；交叉质证注入量小于主席那份。
- `test_agent_llm_path.TestRound2Truncation`（4 例）：让假端点**只对委员的质证
  轮**返回截断输出，断言整场仍然出得来决议、沿用被写进会议问题、第二轮成员
  的轮次标记仍是 1（残稿没有混进计票）、主席拿到的都是可用结论。
- `tools/mock_llm.py` 加了 `FINPULSE_MOCK_TRUNCATE=peers`，手动也能复现。

**回归有效性验证过**（两次都把改动退回旧行为，看用例变红）：

- 把 `turn_budget` 换回常量 4 → `test_模型一轮只调一个工具也写得完报告` 失败：
  `AssertionError: 4 != 5 : 一共问了 4 轮` —— 正好复现"轮数花在取数上"。
- 把截断改回写 `run.error` → `test_截断但段落齐全的报告仍然可用` 失败：
  `截断又被当成错误了：（第 3 轮输出被 max_tokens 截断）`。
- 把沿用兜底摘掉 → `TestRound2Truncation` **4 例全红**，且报错文字与线上
  逐字一致：`有效委员 0 位（[]），未达 quorum 2 位`。

另外用真实 CLI + 假端点跑了一遍人眼可见的路径：截断场景下报告正常给出
`BULLISH`，并打印出沿用告警；不截断时一切照旧。

### 18.8 教训

- **两处预算之间的不等式要显式写出来。** `max_tool_calls=6` 与
  `MAX_TURNS=4` 单独看都合理，放一起就是自相矛盾。常量式的"上限"必须
  从它要服务的东西推导，否则改一个忘一个。
- **"没写完"和"没写"是两件事。** 把前者按后者处理，看起来像严格，实际是
  把最容易发生的边界情况（正好写满）变成了致命错误。
- **一轮的失败只属于那一轮。** 编排层在最终一轮上做全局判定，等于让任何
  一次瞬时故障都能追溯地否定此前所有已成立的结论。有状态的过程要能
  "降级到上一个可用状态"，而不是清零。
- **降级必须可见。** 沿用上一轮如果不写进报告，读的人会以为质证真的发生过
  —— 那比直接报错更糟，因为它产出的是一个看起来合格的假象。
- **报错要能指向动作。** "报告不可用" → 说明白是截断还是缺段；前者调
  `max_tokens`，后者修提示词，两个动作完全不同。

## 19. 接上 DeepSeek 后终于跑通了，但报告里冒出 26 条"数字无法溯源"

### 19.1 现象

上一节把轮数/截断/沿用三件事修完，用户重跑 DeepSeek：

```
决议      BEARISH / MEDIUM
会议问题  [warning] 第 2 轮以下委员未产出可用结论，已沿用其第 1 轮立场：
          technical_analyst（…缺：「终端证据、置信度」）
会议问题  [warning] technical_analyst.number_provenance：8 个数字无法溯源
会议问题  [warning] flow_analyst.number_provenance：8 个数字无法溯源
会议问题  [warning] risk_officer.number_provenance：4 个数字无法溯源
会议问题  [warning] committee_chair.number_provenance：26 个数字无法溯源
```

**决议这次是对的、质证也真的发生了**（改口 2 人）。但主席那份报告的
26 条告警不可能是真的 —— 它自己在报告里写着"我用 stats 复核了…全部一致"。

### 19.2 根因：池子按"它调了什么工具"建，而报告是引用出来的

把主席报告里的数字逐个对号：

| 报告里的数字 | 真实出处 | 在主席的池子里？ |
|---|---|---|
| ma5/ma20/ma60 1245.26 / 1273.42 / 1288.79 | `indicators.ma` | ❌ |
| MACD DIF -14.7693 / DEA -12.5702 | `indicators.macd` | ❌ |
| 20 根均量 2,579,611 / 全样本 4,019,941 | `flow.recent_avg_volume` / `avg_volume` | ❌ |
| 量比 0.642 / 上涨下跌比 1.135 | `flow.volume_ratio` / `up_down_volume_ratio` | ❌ |
| 15.31% / 22.1% 分位 | `flow.volatility_regime` | ❌ |
| 技能分 -0.3043 | `backtest.skill` | ❌ |
| MDD -24.8469% / VaR95 / CVaR95 / 偏度 1.4689 / 峰度 6.7879 / 峰谷 92·182 | `stats` | ✅ |

**`stats` 那几个全过了，恰好 26 个非 `stats` 的数字全被判"无法溯源"。**
下标一一对上，根因没有歧义：

```jsonc
// committee_chair.json —— 主席的工具清单只有一项
"tools": ["stats"]
```

```text
// 可它的提示词里写着：
你**不能引入新的数据**。你手上只有各人的结论与他们的工具输出。
2. 调用 stats 核对至少两个被引用的数值是否与数据一致。
```

**提示词要求它引用各分析师的判据并交叉核对，池子却只装它自己调的那个工具。**
它引用的均线来自技术面的 `indicators`、量比来自量价的 `flow`、技能分来自
风险官的 `backtest` —— 这些数字是通过**注入的对等结论**进入它的视野的，
不是它自己算的。引用它们是履职，不是编造。

### 19.3 修法一：池子按"模型读过什么"建

数字溯源要回答的是"这个数是不是凭空来的"。那么判据只能是**模型读到过什么**，
而不是**它调了哪些工具**。后者是前者的真子集，差得还挺远。

所以 `GuardrailContext` 多一个 `prompt_text`，装该角色本轮收到的任务提示词
原文（运行参数 + 其它角色的结论），池子改成：

```python
pool = number_pool(ctx.tool_results) | number_pool(ctx.prompt_text)
```

链路上只需要一处改动：`roles.py` 里本来就把这份提示词拼出来当 user 消息，
现在留一份引用，交给 `_check`。**提示词是按角色各拼各的**（主席拿全文 1600 字，
委员拿 900 字），所以池子也天然按"这个人实际读到的"划 —— 截断掉的部分不算
出处，这一点是对的。

用用户那份真实报告复原验证（`tool_results` 只放 `stats`、`prompt_text` 放三位
分析师的节选）：

```
修前：池子只有 stats        → [warning] 21 个数字无法溯源：1245.26、1273.42… 等 21 处
修后：池子 += 提示词        → 无告警
```

### 19.4 修法二：认可"由池中两数相除算出的比值"

池子修完还剩一类误报：**模型自己算出来的比值**。提示词本来就要求分析师做
这类换算（量比、占比、相对强弱、倍数），模型照做了，而池子里装的是它的
原料、不是它的成品。

新增 `_is_derived`：池中任意两数相除的商，若与报告里的字面量按精度吻合，
即视为有出处。带 `%` 的字面量同时比"小数形态"（`16.0%` ↔ `4/25 = 0.16`）。

**刻意只认除法，不认加减乘。** 这不是省事，是必须：

- 池子里任意两数**相乘或相加**会覆盖极大一片数值区间 —— 随便编一个价位
  都能撞上其中一个，护栏直接等于删掉；
- 除法的商落在有限的几个量级上，既覆盖了真正会被引用的比值，又给编造的
  绝对值留不下多少藏身处。

另外把商限定在 `0.001 ~ 100`：超出它的多半是**量纲不同**的两个数相除
（成交量 ÷ 价格 ≈ 3194），那种商不是分析里会引用的数，却正好会给编造的
绝对值当藏身处。测试 `test_衍生比值不接受量纲不同的两个数相除` 钉住这条。

### 19.5 两处措辞

**① 沿用理由不再套娃。** 用户贴回来的那行是：

```
technical_analyst（本轮未产出可用结论（输出被 max_tokens 截断，段落没写完，缺：「终端证据、置信度」））
```

外层已经说过"未产出可用结论"，内层又说一遍。`carry_reason` 现在只放
`why_unusable()` 的返回值本身，读起来是：

```
第 2 轮以下委员未产出可用结论，已沿用其第 1 轮立场：flow_analyst（输出被
max_tokens 截断，段落没写完，缺：「波动率状态、背离、终端证据、置信度」）；…
```

**② 告警要把数字本身写进 message。** 报告渲染只显示 `message`（`detail`
进轨迹）。只写"8 个数字无法溯源"，用户拿着报告**没法复核是哪 8 个** ——
一条无法复核的告警，除了制造焦虑没有别的用处。现在写成
`2 个数字无法溯源：1.86%、3194.70`。

### 19.6 测试

新增 9 例（Python 522 → 531）：

- `test_agent.TestGuardrails`（6 例）：提示词里的数字（别人的工具输出、
  运行参数）算出处；**提示词里没有的数字照样抓**；池中两数相除的比值算
  出处；百分数形态的比值同样算；量纲不同的除法不算出处；告警的 message
  里必须带具体数字。
- `test_agent.TestRoleRuntime.test_task_prompt_reaches_the_guardrails`（1 例）：
  用只记录上下文的假护栏，断言提示词原文（对等结论 1500.25、运行参数
  最小训练样本 60）确实送到了护栏，**且这两个数都不在主席自己的工具输出里**
  —— 后半句是关键，少了它这条测试绿得毫无意义。
- `test_agent_llm_path.TestChairCitesPromptNumbers`（2 例）：让假主席真的
  引用一个只存在于提示词里的运行参数，断言它的报告**零** `number_provenance`
  告警。另一条先确认"确实引用了"，防止用例空转。
- `tools/mock_llm.py` 加 `FINPULSE_MOCK_CITE=params`，手动也能复现。

**回归有效性验证过**（把改动逐个退回旧行为，看用例变红）：

- 把提示词从池子里摘掉 → `test_主席报告没有数字溯源告警` 失败；
- 把 `_is_derived` 改成恒返回 False → 两条比值用例全红。

**这里差点留下一个空转的测试**：百分数比值那条最初写成 `16.0% = 4/25`，
看着合理，可是 `16.0 ≤ SMALL_INT_MAX(32)`，会被"小整数一律放行"那条白名单
兜住 —— 池子怎么建它都不会红。换成 `62.5% = 5000000/8000000` 才咬得住。
**验证过用例会红，才知道它到底在测什么。**

### 19.7 教训

- **判据要按"系统该拦什么"来定，不是按"数据在哪最方便取"。** 溯源要拦的是
  "凭空来的数"，那么"模型读到了什么"才是唯一正确的边界。用"它调了什么工具"
  近似它，看着省事，实际每次都会错一整类。
- **提示词注入的内容是"模型的知识边界"。** 只要往提示词里塞了别人的结论，
  那些结论里的数字就自动成为合法出处 —— 引用它们不叫幻觉。这一点在
  做多 agent 编排时特别容易漏，因为每个角色的"输入"和"它自己拉的数据"
  根本是两回事。
- **护栏的放行规则必须针对"合法写法"逐个补，但每补一条都要问它会不会把护栏
  掏空。** 加法乘法不能认，因为它们的值域太宽；除法可以认，但要限量纲。
  这条线不是凭直觉画的，是"编造的数能不能藏进去"推出来的。
- **放行规则要有反向测试守着。** 允许衍生的同时必须有一条"编造的绝对值仍然
  被抓"的用例，否则下一次有人顺手放宽容差时，没有任何东西会拦住他。
- **告警必须可复核。** 只说条数不说内容，等于把核查工作推给一个拿不到数据的人。

## 20. 「会议问题」这块牌子：一次命名歧义，外加两类溯源误报

### 20.1 现场

第 4 次用真 DeepSeek 跑，终于跑出了一份**正确**的报告（BEARISH / MEDIUM，
分歧记录逐条对得上），但用户盯着头部问了一句：

> 会议问题不应该是一个应用系统提示词的感觉吗？比如说"对当前页面的股票和
> 数据讨论是否值得投入"类似这种的，你需要先判断我的判断正不正确。

同一条消息里还留了一句"注意会议问题部分还是有问题，但是下面的输出感觉是
正确的"——两件事，得分开判。

### 20.2 判定：对了一半，另一半是误诊

**对的是命名。** `会议问题` 就是引擎返回的 `out.problems`
（`CliApp.cpp:640` / `MainWindow.cpp:240` 都是 `kv("会议问题", prob)`），
它的本义白纸黑字写在 `AgentService.h:183` 的注释里：**"会议层面的问题
（含 quorum 不足的原因）"** —— 是"会议过程中出的问题"，不是"会议要议的问题"。
可中文里后一种读法同样自然，用户就是那么读的。**一块牌子挂两种意思，
把人带偏的是命名。**

**误诊的是内容。** "告警不该出现在这里"不成立：这次的 `output_truncated`
说明量价分析师那轮真被截断了（该调 `max_tokens`），`number_provenance`
哪怕误报，这条护栏本身也是整套系统最有价值的一条。problems 的三个来源
（配置体检 / quorum 与沿用 / 各角色护栏）都合法可操作，删掉等于删掉
排障能力。

**用户真正想要的东西确实缺失，但不在这一栏。** "对当前页面的股票和数据
讨论是否值得投入"是**议题**。查下来议题通道从头到尾是空的：

| 位置 | 情况 |
|---|---|
| `AgentOptions`（`AgentService.h:69-97`） | 没有任何议题 / 问题字段 |
| `DebateResult`（`orchestrator.py:202`） | 没有 |
| `build_task_prompt`（`roles.py:181`） | 只写运行参数，**不写"问题"** |
| `RoleRuntime.run(instruction=...)` | 全仓**零调用点**，只有 `roles.py:319` 一处形参转发 |

所以报告头部只有一个"会出了什么问题"的通道，没有一个"这场会在议什么"的
通道。该补的是后者，该改的是前者的牌子。

### 20.3 顺带验出一处真 bug：溯源护栏的两类误报

用户说"会议问题部分还是有问题"——这次是对的。写探针复现（池子装 `stats`
的**带符号**原值），三类机制里有两类是我们的错：

| 类别 | 机制 | 本次对应 |
|---|---|---|
| **A 非 ASCII 负号** | 模型写 `−14.2606`（U+2212），而 `_NUMBER_RE` 的 `[-+]?` 只认 ASCII → 抽出**无符号**的 `14.2606` 去和池子里的 `-14.2606` 比 | 主席 `14.2606`、`24.8469` |
| **B 幅度 vs 符号** | 工具返 `max_drawdown_pct = -24.8469`，报告写「最大回撤 24.85%」——回撤为负、幅度为正，人话里说的就是后者 | 风险官 `24.85%`、`1.7346%` |
| C 纯减法衍生 | `148 = 250 − 102`，`_is_derived` 设计上只认可除法 | 主席 `148`（**取舍，非 bug**） |

**类 A 的决定性证据**：告警里打出的字面量是 `14.2606`、`24.8469`，**没有
负号**。而 `guardrails.py:252` 是 `unmatched.append(token)` —— 原文若用 ASCII
的 `-`，打出来必然带负号。所以模型写的确实是 U+2212。

（同轮技术面那 6 个离线判不了，但有个旁证：`finpulse-cli` 实测同一标的的
`macd=-14.7693`，恰好就是它被判"无法溯源"的数之一 —— 综合判断同属类 A。）

**还有一个容易看漏的点**：`_canonical_number` 里明明写着
`t.lstrip("+")`，负号是**保留**的，看起来没问题。但正则先一步把 U+2212
挡在门外，负号根本没进 token —— **查符号类 bug 要看"正则收不收得到"，
不是看后面怎么处理 token。**

### 20.4 改法

**Python 侧（引擎）**

1. `schemas.normalize_signs()`：把 `U+2212 / U+FF0D / U+2013 / U+2014`
   统一成 ASCII `-`，挂在 `extract_numbers()` 入口 —— 一处覆盖
   `number_pool` / `numbers_in_text` / 护栏三处调用者。
2. `NumberProvenance._matches()`：**没写符号按幅度比，显式写了符号按符号比。**
   后者是模型的断言，翻了号（工具给 `+14.2606`、报告写 `-14.2606`）仍然要报。
   放宽的只是"模型没表态"的情形。
3. `roles.describe_intent(ctx)`：从 `build_task_prompt` 里把运行参数那一段
   抽成函数，提示词与报告头部**共用同一句**；新增 `DebateResult.intent`
   随结果回传；单角色路径（走 `agent.run`，没有 `DebateResult`）由门面层
   `api.AgentService.run_role` 补上。

**C++ 侧（展示）**

4. `Outcome` 加 `intent` 字段并在两条解析路径里读出。
5. `会议问题` → `运行告警`，另起一行 `议题`。

**顺带修掉一处错的注释**：`render_outcome` 上方原本写着"因此可以被单独测试
（见 `tests/test_eventtext.cpp`）"——匿名命名空间的东西别的翻译单元根本看不见，
而 `test_eventtext.cpp` 测的是 `EventText.h`。这条函数**没有直接单测**，
注释已在原处更正并说明真实覆盖面（`test_agentservice.cpp` 压 Outcome 字段）。

### 20.5 差点又留下一个空转测试

类 A 的第一条用例写的是"报告写 U+2212、池子里是负数 → 不该报"。把归一化
退回旧行为，它**照样绿** —— 因为幅度匹配把 U+2212 丢掉符号的后果兜住了。
拿它验证归一化等于没测。

真正能咬住的是另一条：**池子里放正数、报告写 U+2212 负号，必须报**
（符号断言不能被丢掉）。两条并存才完整：一条守"别误报"，一条守"别把断言
也一起放过"。

四个回归点全部验过红：`normalize_signs` 退回恒等 → 两条 A 类用例红；
摘掉幅度分支 → B 类用例红；`to_json` 去掉 `intent` → 议题用例红。

### 20.6 测试与验证

- Python **531 → 538**（+7：3 条溯源、1 条"议题与提示词同源"、1 条编排
  `intent` 序列化、另 2 条为同源拆分出的抽取级用例），C++ **157 / 157**。
- 构建零告警（`build/` 与 `~/finpulse-gui-build` 各一遍）。
- 端到端实跑 CLI：干净跑（规则后端）只出「议题」一行；挂
  `FINPULSE_MOCK_TRUNCATE=peers` 的假后端跑，头部同时出现
  「议题」与「运行告警（沿用其第 1 轮立场）」两条，措辞与预期一致。

### 20.7 教训

- **标签是接口。** "会议问题"四个字里，`问题` 既可以是"故障"也可以是"议题"。
  一个词承载两种语义，用户迟早会按另一种读法理解——而且他会以为自己看到的
  是 bug。**改一个标签的成本，远低于解释一次误会。**
- **报告要能自证。** 只在头部给结论和告警、不给口径，等于把复核的门槛抬到
  "你得先知道我用了哪段数据"。议题这一行补的就是这个。
- **同一件事的措辞只能有一份来源。** 提示词里那句和报告头部那句共用
  `describe_intent()`；两处各写一遍，漂移出来的 bug 最难查——它不报错，
  只是"模型被告知的"与"用户以为它被问的"悄悄变成两件事。
- **误报的代价不是"多一条"，而是"整条护栏作废"。** 这是第二次栽在同一类
  问题上（第一次是池子边界）。凡是"每次都报"的告警，都得当成 P0 修。
- **放宽判据要成对设计。** 认了幅度匹配，就必须配一条"显式翻号仍要报"的
  反向用例；否则下一次有人顺手再放宽，没有任何东西会拦住他。
- **退一步确认用例会红。** 这已经是本项目第四次踩"空转测试"了——写得
  像模像样、代码怎么改它都不红。**只有见过它红，才知道它在测什么。**

## 21. 「双击 run-gui 看不到界面」：一个不在本项目里的故障

**现象。** 双击 `scripts/run-gui.cmd`，控制台一闪，界面没了。

**先证明"不是我们的锅"。** 全部离线可查，而且每一条都必须做：

| 检查 | 结果 |
|---|---|
| `~/finpulse-gui-build/src/gui/finpulse-gui` 在不在 | 在，1.2MB，时间戳是今天的构建 |
| 进程能不能活 | 能。`timeout 20` 跑满 20 秒被掐（rc=124），不是自己退的 |
| 界面内容对不对 | 对。`QT_QPA_PLATFORM=offscreen --screenshot` 出的 PNG 135KB，有内容 |
| 动态库缺不缺 | `ldd` 无 `not found` |
| 窗口有没有到 Windows | **到了**。`msrdc.exe`（WSLg 的窗口宿主）的标题是 `[WARN:COPY MODE] FinPulse Terminal v0.4.0 …` |

最后一行就是答案的前半截：**窗口建出来了，但标题上挂着 `[WARN:COPY MODE]`。**

**后半截在 WSLg 的日志里。**

```
$ grep -n 'rdp_allocate_shared_memory\|use_gfxredir' /mnt/wslg/weston.log
67: rdp_allocate_shared_memory: Failed to open "/mnt/shared_memory/{…}" with error: Input/output error
68: RDP backend: use_gfxredir = 0
```

WSLg 把 Linux 窗口送上 Windows 桌面，要先在 `/mnt/shared_memory` 分配共享内存做帧
传输；分配失败就关掉图形重定向（`use_gfxredir = 0`）退回逐帧拷贝 —— 也就是
**copy mode**：窗口照建、标题照给，内容永远画不出来。这正是微软 issue
[microsoft/wslg#972](https://github.com/microsoft/wslg/issues/972)。对照干净会话，
日志里只有 `use_gfxredir = 1`，没有那行报错。

**关键性质：这是每个 WSLg 会话重新掷一次的骰子。** 实测四次冷启动，两次坏两次好；
而本机的 WSL 虚拟机空闲就会关停，所以几乎**每次双击都是一次新掷**。这意味着
"重启 WSL"不是安慰剂，是真正的修复手段 —— 但也意味着用户会反复踩到。

**做了三件事。**

1. `scripts/run-gui.cmd` 加**预检**：`use_gfxredir` 那行在 weston 启动阶段就写好，
   **早于任何应用启动**，所以可以在弹窗口之前判断会话好坏 —— 不会先闪一个空白窗口。
   `wsl -e bash -lc "…grep -q 'use_gfxredir = 0' …"` 的退出码经 `wsl.exe` 原样传回，
   启动器只用 `errorlevel` 判断，不需要抓标准输出。
2. 再留一道**后检**：启动后看 `tasklist /v /fi "IMAGENAME eq msrdc.exe"` 的标题里
   有没有 `COPY MODE`，兜住"日志说好、实际没画"的情况。
3. 命中就问一句要不要 `wsl --shutdown` 重来（最多 3 次）。**问而不是直接重开**：
   那会一并关掉 Docker Desktop 等发行版，可能正在跑容器，不该由启动器替用户决定。

**这个 .cmd 故意写成纯 ASCII。** cmd.exe 按 ANSI 读脚本，UTF-8 中文注释会变乱码；
项目里原有的 `run-cli.cmd` 也是全英文。中文说明放在 `manual.md` 10.1 节，
脚本头部只留一行指针。

**教训。**

- **"界面看不见"和"程序没起来"是两件事。** 前四步（二进制、进程、截图、依赖）
  各花不到一分钟，却把"改代码"这条死路早早排除了；不然会在 MainWindow 里
  白找半天。
- **窗口标题是被低估的诊断面。** `[WARN:COPY MODE]` 前缀直接指向根因；
  在此之前"任务管理器里 msrdc 那个窗口标题"从没被当成过证据。
- **报错的位置决定能不能预检。** 同样一条错误，写在"应用启动时"就只能事后补救，
  写在"合成器启动时"就能提前判断 —— 值得为此专门看一眼日志的时序。
- **非本项目的问题也要收进文档。** 它不属于任何模块，所以最容易在"反正不是我们
  的问题"里被丢掉；代价是用户每次双击都再撞一遍，并且不知道那是已知故障。

## 22. 「结论没提是否值得投资」：一份读完了却不知道所以然的报告

**现象。** 第 4 次真跑（上一节刚把「会议问题」改名并补了议题行）之后，用户说：
「agent 最后的结论没有提到是否值得投资呀」。

**这个判断是对的，而且上一轮我理解偏了。**

上一轮用户说「会议问题不应该是一个应用系统提示词的感觉吗，比如『对当前页面的股票
和数据讨论是否值得投入』」，我判定缺的是**议题**，做法是回显本次运行的参数
（标的 / 样本 / 预测设置）。议题行的措辞没错，但**它是元信息，不是答案**。
用户要的从头到尾是同一件事：**报告得正面回答"值不值得投"**。我给了个
"这场会在议什么"的标签。这一轮把它补上。

**改动。**

| 位置 | 改动 |
|---|---|
| `configs/committee_chair.json` | `output_sections` 在「决议」之后插入「投入判断」；instructions 的输出格式由五段改六段，三档措辞写死 |
| `llm/rule_based.py` | 新增 `@filler("投入判断")`，按会议状态填三档 + 三条依据 + 翻转条件 |
| `tools/mock_llm.py` 与 `tests/test_agent_llm_path.py` 的内联假后端 | 各加一个「投入判断」分支（两个假后端必须同形状） |
| `roles.py` | 未改：输出预算按 `len(output_sections)` 自动 +200 字 |

**为什么放在「决议」之后，而不是压在最末。** 答案要出现在读者开始跳读之前。
顺序是 决议 → 投入判断 → 采纳 → 否决 → 分歧 → 置信度：先给方向和"所以呢"，
再给论证。放末尾的话，读者得读完五段才等到结论 —— 而他往往读不到那里。

**两个边界是写的过程中被打出来的，都不是动手前能想到的。**

1. **全体 NEUTRAL 会被判成「值得投入」。** 第一版按"置信度够不够"判档，于是
   三位分析师都自报 `HIGH`、方向全是 `NEUTRAL` 时，档位落在最好的一档 ——
   一场谁都没给出方向的会，产出了"值得投入"。判据必须**先看方向、再看强度**：
   `NEUTRAL` 是"没有方向"，不是"高置信度地认为中性"。另外"打平"（双方都有票、
   相抵）与"全体中性"（压根没有方向性判断）要分开措辞，否则读者会以为有人看多。
2. **`BEARISH` 时报「值得投入」会被读成「建议买入」。** 这个是**实跑报告**才看出来
   的：「**值得投入** —— 方向 BEARISH，3 位分析师中 2 位支持」。「值得投入」
   这四个字本身不带方向，而方向恰恰是这份报告最要紧的信息。改成
   「支持一次**与决议方向（BEARISH）一致**的投入决策」，并在配置里写明
   "它不是「建议买入」，方向永远以「决议」段为准"。

**边界守住了。** 仓位数量与具体价位仍然不给（`ForbiddenPhrases` 那层没动）：
投入判断回答的是"证据够不够支撑一次决策"，不是下单指令 —— 后者需要资金约束
与风险预算，本系统没有这两样输入，给了就是编。

**测试 538 → 547（+9）**，C++ 157/157 不变（改动全在 Python 侧，无需重编）。

新增：配置契约 1（主席必须有这一段、紧跟「决议」、三档措辞写死）、规则后端分档 6
（过半 / 少数派 / 打平 / 全体中性 / 无下级结论 / 看空方向要写明投什么）、
护栏缺段 1（漏写判 error）、LLM 路径 1（假模型照配置演出的报告里有明确档位）、
编排层 1（规则后端渲染的段落里不许留"本后端没有为…"占位句）。

**回归有效性四点全部验红**（配置删段 / `all_neutral` 恒 False / `@filler` 摘掉 /
假后端分支删掉）。第四点逼出了一条本来会漏的用例：删掉假后端的专用分支后它退化成
通用占位句，而"段落存在"的断言照样通过 —— 所以断言必须查**档位措辞**
（`**值得投入**`），不能只查段名。

**端到端**：规则后端实跑（`finpulse-cli --agent --bars 260 --seed 42`）确认
「## 投入判断」出现在「## 决议」之后；离线假后端跑完整 LLM 路径，主席报告六段齐全、
顺序正确。

**没做的事（留给用户决定）。** 报告头部（CLI 的「决议 / 置信度 / 议题」那几行）
**没有**加投入判断行。理由：那要么从主席正文里抽档位（依赖措辞，脆），要么由编排层
另算一份（造成"头部说 A、正文说 B"的双真相）。真要做，正确做法是让编排层算出档位、
写进主席提示词作为既定事实，再同时供头部使用 —— 一个来源，两处显示。需要改 C++ 重编。

**教训。**

- **"回显了在议什么"不等于"回答了问题"。** 议题行与投入判断段看起来都在讲
  "这次会关于什么"，但一个是元信息、一个是结论。用户抱怨"结论没提到"时，
  缺的就是**结论**。
- **档位判据要先看方向、再看强度。** 只要判据的输入里有"置信度"，就必须先问
  "这个置信度是对什么的置信度"——`NEUTRAL` 角色的高置信度问的是"状态描述可不可靠"，
  与方向无关。把两者混进一个判据，就会在"谁都没方向"的会上给出最强档位。
- **措辞要在真实报告上读一遍。** 「值得投入 + BEARISH」在代码里是两个合法字段，
  在报告里是一句会被误读的话。
